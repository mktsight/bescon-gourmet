# Requirements Document

## Introduction

ベスコングルメ部（部員約9名）の運営を支えるメンバー限定のクラウドサービス（以下「運営サービス」）を新規に構築する。部長が開催イベント（BCG企画）を登録し、部員はログインしてイベント内容を確認し、参加／不参加を回答する。v1（MVP）の範囲はイベント案内と出欠回答のみとする。

イベントの項目は既存フライヤー（山寺編・蔵王ライザ編・上山編・山形駅前編）の記載項目に合わせ、編名・開催日・集合時刻・集合場所・運動内容・ご褒美の食事とする。

運営サービスは AWS のサーバーレス構成（Lambda、API Gateway、DynamoDB、Cognito）上で Node.js 20 により実装し、想定利用量で AWS 無料利用枠に収める。既存のフライヤー生成資産には変更を加えない。

### スコープ外（v1）

- フライヤー（SVG／PNG）の自動生成、およびフライヤー生成スクリプトの Web 化
- メール・LINE 等による通知、リマインド
- イベントへのコメント、チャット、写真共有
- 外部公開ページ、部外者向けの閲覧機能
- 部員による自己アカウント登録

## Glossary

- **運営サービス**: 本仕様で構築する、ベスコングルメ部のメンバー限定 Web サービス全体（ブラウザ画面、API、データ保存、認証を含む）
- **メンバー**: 運営サービスにアカウントを持つ人。部長と部員の総称
- **部長**: イベントの登録・編集・削除および部員アカウントの作成を行う権限を持つメンバー
- **部員**: 部長以外のメンバー。イベントの閲覧と出欠回答を行う
- **認証済みメンバー**: 有効なログインセッションを持つメンバー
- **未認証リクエスト**: 有効なログインセッションを伴わない運営サービスへのリクエスト
- **イベント**: 部長が登録する BCG企画の開催情報。編名・開催日・集合時刻・集合場所・運動内容・ご褒美の食事の6項目を持つ
- **編名**: イベントの名称（例: 「山寺編」「蔵王ライザ編」）
- **開催日**: イベントの開催日（日本時間の暦日）
- **集合時刻**: 開催日における集合時刻（日本時間、24時間表記の時:分）
- **出欠回答**: 1名のメンバーが1件のイベントに対して登録する「参加」または「不参加」の回答
- **未回答**: メンバーが該当イベントに対して出欠回答を登録していない状態
- **回答状況**: 1件のイベントについての、全メンバーの出欠回答（参加・不参加・未回答）の一覧と、それぞれの人数
- **開催予定イベント**: 開催日が日本時間の当日以降であるイベント
- **終了イベント**: 開催日が日本時間の当日より前であるイベント
- **既存フライヤー資産**: `.agents/flyer/` 配下のファイル、`.kiro/skills/bescon-flyer/` 配下のスキル、およびワークスペース直下の既存フライヤー SVG／PNG ファイル
- **AWS無料利用枠**: AWS が提供する Lambda、API Gateway、DynamoDB、Cognito の無料利用枠

## Requirements

### Requirement 1: ログイン

**User Story:** As a メンバー, I want IDとパスワードでログインしたい, so that 部のイベント情報に自分だけがアクセスできる

#### Acceptance Criteria

1. WHEN メンバーが登録済みのメールアドレスと正しいパスワードを送信した, THE 運営サービス SHALL ログインセッションを発行し、イベント一覧画面を表示する
2. IF メンバーが誤ったメールアドレスまたはパスワードを送信した, THEN THE 運営サービス SHALL ログインを拒否し、どちらが誤っているかを特定しない形式のエラーメッセージを表示する
3. WHEN 部長が作成した仮パスワードでメンバーが初回ログインした, THE 運営サービス SHALL イベント一覧画面の表示前に新しいパスワードの設定を求める
4. WHEN 認証済みメンバーがログアウトを操作した, THE 運営サービス SHALL ログインセッションを無効化し、ログイン画面を表示する
5. IF 認証済みメンバーのログインセッションが有効期限切れになった, THEN THE 運営サービス SHALL ログイン画面を表示し、再ログインを求める

### Requirement 2: 部外者からのアクセス遮断

**User Story:** As a 部長, I want 部外者に部の情報が一切見えないようにしたい, so that 部員の予定や集合場所が外部に漏れない

#### Acceptance Criteria

1. IF 未認証リクエストがイベント、出欠回答、または回答状況のデータを要求した, THEN THE 運営サービス SHALL HTTP ステータス 401 を返し、レスポンスにイベント・出欠回答・回答状況のデータを含めない
2. WHEN 未認証の利用者が運営サービスの画面にアクセスした, THE 運営サービス SHALL ログイン画面のみを表示する
3. THE 運営サービス SHALL 部長が作成したアカウントのみをメンバーとして受け付ける
4. IF 利用者が自己アカウント登録を試みた, THEN THE 運営サービス SHALL アカウント登録を拒否する
5. THE 運営サービス SHALL ブラウザと運営サービス間のすべての通信を HTTPS で行う

### Requirement 3: 部員アカウントの作成

**User Story:** As a 部長, I want 部員のアカウントを作成したい, so that 新しい部員が運営サービスを使い始められる

#### Acceptance Criteria

1. WHEN 部長がメールアドレスと表示名を指定して部員アカウントの作成を実行した, THE 運営サービス SHALL 部員アカウントを作成し、仮パスワードを発行する
2. IF 部長が既存アカウントと同じメールアドレスで部員アカウントの作成を実行した, THEN THE 運営サービス SHALL 部員アカウントの作成を拒否し、メールアドレスが登録済みである旨を示す
3. THE 運営サービス SHALL 各メンバーに部長または部員のどちらか1つの役割を割り当てる

### Requirement 4: イベントの登録

**User Story:** As a 部長, I want フライヤーと同じ項目でイベントを登録したい, so that 部員に次回の開催内容を案内できる

#### Acceptance Criteria

1. WHEN 部長が編名・開催日・集合時刻・集合場所・運動内容・ご褒美の食事の6項目を入力して登録を実行した, THE 運営サービス SHALL イベントを保存し、登録したイベントの詳細画面を表示する
2. IF 部長が6項目のいずれかを空欄のまま登録を実行した, THEN THE 運営サービス SHALL イベントを保存せず、空欄の項目名を示すエラーメッセージを表示する
3. IF 開催日が YYYY-MM-DD 形式の実在する日付でない, THEN THE 運営サービス SHALL イベントを保存せず、開催日の形式エラーを表示する
4. IF 集合時刻が 00:00 から 23:59 の範囲の HH:MM 形式でない, THEN THE 運営サービス SHALL イベントを保存せず、集合時刻の形式エラーを表示する
5. IF 編名が30文字を超える、集合場所が100文字を超える、または運動内容もしくはご褒美の食事が200文字を超える, THEN THE 運営サービス SHALL イベントを保存せず、上限を超えた項目名と文字数上限を示すエラーメッセージを表示する
6. WHEN 運営サービスがイベントを保存した, THE 運営サービス SHALL 全メンバーの出欠回答を未回答として扱う

### Requirement 5: イベントの編集と削除

**User Story:** As a 部長, I want 登録済みのイベントを修正・取り消ししたい, so that 予定変更や中止を部員に正しく伝えられる

#### Acceptance Criteria

1. WHEN 部長が登録済みイベントの項目を変更して保存を実行した, THE 運営サービス SHALL 変更後の内容でイベントを更新する
2. THE 運営サービス SHALL イベント編集時の入力内容に対して、Requirement 4 の受け入れ基準 2〜5 と同一の入力検証を適用する
3. WHEN 運営サービスがイベントを更新した, THE 運営サービス SHALL 該当イベントに登録済みの出欠回答を保持する
4. WHEN 部長がイベントの削除を実行した, THE 運営サービス SHALL 削除の確認を求める
5. WHEN 部長がイベントの削除を確認した, THE 運営サービス SHALL イベントと該当イベントに紐づくすべての出欠回答を削除する

### Requirement 6: 役割による操作の制限

**User Story:** As a 部長, I want イベントの登録・変更は部長だけができるようにしたい, so that 案内内容が意図せず書き換えられない

#### Acceptance Criteria

1. IF 部員がイベントの登録、編集、または削除を要求した, THEN THE 運営サービス SHALL 要求を拒否し、HTTP ステータス 403 を返す
2. IF 部員が部員アカウントの作成を要求した, THEN THE 運営サービス SHALL 要求を拒否し、HTTP ステータス 403 を返す
3. WHILE 部員としてログインしている, THE 運営サービス SHALL イベントの登録・編集・削除およびアカウント作成の操作部品を画面に表示せずに各画面を表示する

### Requirement 7: イベントの閲覧

**User Story:** As a 部員, I want 登録されたイベントの内容を確認したい, so that いつ・どこに集合して何をするのかがわかる

#### Acceptance Criteria

1. WHEN 認証済みメンバーがイベント一覧画面を開いた, THE 運営サービス SHALL 開催予定イベントを開催日の昇順で表示する
2. WHEN 認証済みメンバーがイベント一覧画面で終了イベントの表示を選択した, THE 運営サービス SHALL 終了イベントを開催日の降順で表示する
3. THE 運営サービス SHALL イベント一覧の各イベントについて、編名、開催日、集合時刻、および閲覧中のメンバー自身の出欠回答（参加・不参加・未回答）を表示する
4. WHEN 認証済みメンバーがイベント一覧からイベントを選択した, THE 運営サービス SHALL 該当イベントの6項目すべてと回答状況を含む詳細画面を表示する
5. WHEN 運営サービスが開催日を表示する, THE 運営サービス SHALL 「2026年11月14日（土）」の形式で曜日を付けて表示する
6. IF 認証済みメンバーが存在しないイベントを要求した, THEN THE 運営サービス SHALL HTTP ステータス 404 を返し、イベントが見つからない旨を表示する
7. WHILE 登録済みの開催予定イベントが0件である, THE 運営サービス SHALL イベント一覧画面に開催予定のイベントがない旨を表示する

### Requirement 8: 出欠回答

**User Story:** As a 部員, I want イベントに参加か不参加かを回答したい, so that 部長が人数を把握してお店を予約できる

#### Acceptance Criteria

1. WHEN 認証済みメンバーが開催予定イベントの詳細画面で「参加」または「不参加」を選択した, THE 運営サービス SHALL 選択された回答をそのメンバーの出欠回答として保存する
2. WHEN 出欠回答を登録済みのメンバーが別の回答を選択した, THE 運営サービス SHALL 既存の出欠回答を新しい回答で置き換える
3. THE 運営サービス SHALL 1名のメンバーにつき1件のイベントあたり最大1件の出欠回答を保持する
4. THE 運営サービス SHALL 部長と部員の双方から出欠回答を受け付ける
5. IF 認証済みメンバーが終了イベントに対して出欠回答を送信した, THEN THE 運営サービス SHALL 出欠回答を保存せず、受付が終了している旨を表示する
6. IF 出欠回答の値が「参加」「不参加」以外である, THEN THE 運営サービス SHALL 出欠回答を保存せず、HTTP ステータス 400 を返す
7. THE 運営サービス SHALL 出欠回答の登録者を、送信内容ではなくログインセッションのメンバーとして記録する

### Requirement 9: 回答状況の確認

**User Story:** As a 部長, I want 誰が参加で誰が未回答かを一目で確認したい, so that 店の予約人数を決めたり未回答者に声をかけたりできる

#### Acceptance Criteria

1. WHEN 認証済みメンバーがイベント詳細画面を開いた, THE 運営サービス SHALL 参加・不参加・未回答それぞれの人数を表示する
2. WHEN 認証済みメンバーがイベント詳細画面を開いた, THE 運営サービス SHALL 参加・不参加・未回答それぞれに該当するメンバーの表示名を一覧で表示する
3. WHEN 運営サービスが出欠回答を保存した, THE 運営サービス SHALL 以降に表示する回答状況に保存済みの出欠回答を反映する

### Requirement 10: 実行環境と運用コスト

**User Story:** As a 部長, I want 費用をかけずに運営サービスを運用したい, so that 部費を使わずに続けられる

#### Acceptance Criteria

1. THE 運営サービス SHALL AWS Lambda、Amazon API Gateway、Amazon DynamoDB、Amazon Cognito で構成するサーバーレス構成で稼働する
2. THE 運営サービス SHALL サーバー側の処理を Node.js 20 ランタイムで実行する
3. WHILE メンバー数が10名以下かつ月間の API リクエスト数が10,000件以下である, THE 運営サービス SHALL AWS無料利用枠の範囲内で稼働する
4. THE 運営サービス SHALL 常時稼働の仮想サーバーやデータベースインスタンスを使用せずに稼働する
5. THE 運営サービス SHALL AWS の認証情報やシークレットをソースコードに含めずに、環境変数または AWS のマネージドな設定機構から取得する

### Requirement 11: 既存資産との分離

**User Story:** As a 部長, I want 既存のフライヤー作成環境をそのまま使い続けたい, so that 運営サービスの導入でフライヤー作成が壊れない

#### Acceptance Criteria

1. THE 運営サービス SHALL 既存フライヤー資産から独立した新規ディレクトリに配置する
2. WHEN 運営サービスのソースコード一式が追加された, THE 既存フライヤー資産 SHALL 追加前と同一の内容を保持する
3. THE 運営サービス SHALL 自動テストを Node.js 標準の `node:test` で実行する

## 設計フェーズへの申し送り

- Amazon API Gateway の無料利用枠はアカウント作成後12か月間に限られる。13か月目以降は API Gateway の利用料が発生するが、Requirement 10.3 の想定利用量では月額 1 米ドル未満の見込み。設計時に API Gateway の種類（HTTP API／REST API）と合わせて費用を確認する。
- ブラウザ画面（静的ファイル）の配信方法は要件に含めていない。Requirement 10 の構成と無料利用枠に収まる方法を設計で選定する。
- 部員アカウントの作成手段（運営サービスの画面、AWS コンソール、またはスクリプト）は設計で決定する。Requirement 3 の受け入れ基準を満たせばよい。
- 既存コードは外部パッケージを使用していない。外部パッケージを追加するかどうか（Lambda の Node.js 20 ランタイムに同梱される AWS SDK for JavaScript v3 の利用を含む）は設計で決定する。
